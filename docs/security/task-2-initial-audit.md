# Task 2: Initial Guest, Invitation, and RSVP Audit

## Scope and method

This is an evidence-based review of the current guest, invitation, and public RSVP implementation. It covers the backend models, schemas, API routes, frontend invitation/link workflows, migrations, and existing tests inspected before Task 2 implementation. It is not a certification of the complete platform or its production hosting.

No database records were changed during this initial review. No tests had been run for this Task 2 review at the time this document was written.

## Existing implementation

- Guests belong to an event and have optional name, email, phone, group, RSVP status, plus-one count, an invitation expiry, and RSVP/function relationships. See `backend/app/models/guest.py:20-45`.
- Guest list/create/update/delete, CSV import, group, function assignment, and token endpoints are implemented in `backend/app/api/guest_routes.py:40-317`. The event-scoped routes call `require_event_permission`; guest-specific routes authorize against the guest's event.
- Guest serializers omit the raw token. The authorized token retrieval and rotation endpoints nevertheless return it to users with `guest.update` permission: `backend/app/api/guest_routes.py:284-318`.
- Public RSVP invitation lookup returns the invited guest's name, event name/date/location, assigned function names/date/venue, and that guest's response statuses. It does not return their email or phone: `backend/app/api/rsvp_routes.py:37-64`.
- RSVP submission uses the bearer token, validates status, limits plus-ones to 20, validates function membership, and upserts one row per guest/function. The database enforces uniqueness for `(guest_id, function_id)`: `backend/app/api/rsvp_routes.py:14-18,67-102`; `backend/app/models/rsvp.py:5-18`.
- Guest RSVP tokens are currently plaintext database values. The separate public digital-invitation share tokens are also plaintext and included in authorized invitation API serialization: `backend/app/models/guest.py:30`; `backend/app/models/invitation.py:23`; `backend/app/api/invitation_routes.py:30-40`.
- Guest links are fetched from the API and copied to the clipboard. The frontend also puts the bearer token in `/invite/:token`, and public RSVP lookup currently sends it as a GET path parameter: `frontend/src/pages/workspace/WorkspacePages.tsx:703-716,2318-2355`; `frontend/src/features/rsvp/api/rsvpApi.ts:17-24`.
- Expiration is checked on public RSVP lookup and submission. The expiry migration gives existing guest tokens an expiry; publishing a separate digital invitation issues a share token and expiry: `backend/app/api/rsvp_routes.py:26-34`; `backend/migrations/versions/71cd20f4a8b3_invitation_token_expiry.py`; `backend/app/services/invitation_service.py:8-15`.
- Flask-Limiter is configured, but the inspected public RSVP and invitation routes have no endpoint decorators or application-level limits. The default limiter storage URI is `memory://`, which does not provide shared multi-instance enforcement: `backend/app/extensions.py:9`; `backend/app/config/__init__.py:53-55`; `backend/app/api/rsvp_routes.py:37,67`; `backend/app/api/invitation_routes.py:129`.
- Guest request validation checks name length, email syntax, phone length, and group length; phone syntax and application-specific attendee limits are not checked. RSVP status, plus-ones, dietary-note length, and function membership are validated, but no RSVP deadline or per-guest party-size cap is present in the inspected code: `backend/app/schemas/guest_schema.py:4-13`; `backend/app/api/rsvp_routes.py:14-22,74-84`.
- Existing API permissions are workspace/event scoped through `require_event_permission`; the initial review did not establish direct-request coverage for every role and every guest/invitation endpoint. Relevant implementation: `backend/app/api/guest_routes.py:25-37`; `backend/app/api/invitation_routes.py:20-28`.
- Guest creation, editing, deletion, token rotation, public invalid-token attempts, RSVP changes, and exports did not have explicit security audit events in the inspected guest/RSVP routes. Guest export is performed in the frontend from the currently loaded guest list: `frontend/src/pages/workspace/WorkspacePages.tsx:764-780`.
- The notification model is a user-facing notification record; the inspected guest/RSVP implementation does not show guest-targeted email/SMS/WhatsApp delivery or delivery-status tracking: `backend/app/models/notification.py`.
- The frontend workspace seed data includes named example guests, although the authenticated guest page loads its guest list from the API and clears the list when signed out: `frontend/src/data/workspaceData.ts:45-52`; `frontend/src/pages/workspace/WorkspacePages.tsx:601-635`.

## Findings and required work

| Finding | Initial status | Evidence | Required work |
|---|---|---|---|
| RSVP bearer tokens are stored in plaintext and can be retrieved repeatedly by an authorized user. | Vulnerable | `backend/app/models/guest.py:30`; `backend/app/api/guest_routes.py:284-318` | Add a SQLite-compatible data-preserving migration to hash existing tokens, clear plaintext values, and make all runtime lookup use hashes. Return a newly generated raw token only once when explicitly issuing/rotating a link. |
| Digital invitation share tokens are stored and serialized as plaintext. | Vulnerable | `backend/app/models/invitation.py:23`; `backend/app/api/invitation_routes.py:30-40,129-146` | Hash share tokens at rest, migrate published records without breaking their existing links, and avoid returning persisted token material from ordinary invitation responses. |
| Tokens in public URL paths can be captured by access logs, browser history, or referrer handling. | Partial | `backend/app/api/rsvp_routes.py:37`; `backend/app/api/invitation_routes.py:129`; `frontend/src/routes/AppRouter.tsx:49`; `frontend/src/pages/workspace/WorkspacePages.tsx:2318` | Move API token validation to request bodies, prevent referrer leakage on public invitation pages, and document that the guest-facing URL itself necessarily acts as a bearer credential. |
| Public token lookup/submission is not rate-limited at the route level. | Missing | `backend/app/api/rsvp_routes.py:37,67`; `backend/app/api/invitation_routes.py:129`; `backend/app/extensions.py:9` | Apply sensitivity-appropriate IP and invalid-token limits, return 429 with retry metadata, and require shared rate-limit storage in production. |
| RSVP accepts a fixed plus-one maximum but has no event/guest-specific cap or deadline. | Partial | `backend/app/api/rsvp_routes.py:14-22,74-84`; `backend/app/models/rsvp.py:13-16` | Add persisted RSVP deadline and attendee cap fields/configuration only if supported by the product workflow; enforce server-side and test boundary conditions. |
| Guest phone validation is length-only; import does not reject duplicate contacts or enforce per-row field constraints beyond parser checks. | Partial | `backend/app/schemas/guest_schema.py:4-13`; `backend/app/utils/csv_parser.py`; `backend/app/api/guest_routes.py:163-189` | Normalize and validate contact fields and CSV rows consistently, with clear errors and bounded upload/row count. Avoid inventing uniqueness rules without product confirmation. |
| Guest and public RSVP security actions are not explicitly audited. | Missing | `backend/app/api/guest_routes.py:40-318`; `backend/app/api/rsvp_routes.py:37-102`; `backend/app/models/notification.py` | Add privacy-minimized audit events for management actions, token lifecycle events, RSVP changes, invalid access, and exports. Never store raw tokens or full guest records in logs. |
| Existing guest workspace seed data contains sample personal-looking names and email addresses. | Present in frontend seed data | `frontend/src/data/workspaceData.ts:45-52` | Remove named guest PII from shipped sample data or ensure it is clearly synthetic and never presented as a real account guest list. |
| Family/planner/vendor access is permission checked at event scope, but the initial evidence does not cover every role/action combination. | Partial verification | `backend/app/api/guest_routes.py:25-37`; `backend/app/api/invitation_routes.py:20-28` | Add direct API tests for tenant isolation and applicable roles; retain existing authorization rules. |
| No guest notification delivery workflow was established in the inspected implementation. | Cannot verify as a supported feature | `backend/app/models/notification.py`; guest/RSVP routes | Document notifications as unsupported unless a real provider and delivery workflow are found; do not report WhatsApp/SMS/email as delivered. |

## Verification plan

Before Task 2 can be marked verified, run the focused guest/invitation/RSVP and workspace suites, direct cross-workspace API tests, migration upgrade/downgrade checks against disposable SQLite databases, the full backend suite, and the frontend production build. Production rate-limit storage, proxy/IP configuration, token-bearing link handling by infrastructure, retention policy, and legal/privacy requirements require separate deployment or policy review.
